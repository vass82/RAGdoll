.. _http_api:

HTTP API reference
==================

RAGdoll exposes a small JSON API built with `FastAPI <https://fastapi.tiangolo.com/>`_.
This page describes the HTTP interface as seen by a client. The Python classes
behind it are described in the :ref:`python_api` reference.

The examples assume that the server is running locally with the command from
:ref:`tutorial_local_setup`:

.. code-block:: bash

   uv run uvicorn app.main:app --host 127.0.0.1 --port 8000

The Docker image uses the same application and listens on port ``8000`` as
well (see :ref:`tutorial_docker_setup`).

Endpoints
---------

.. list-table::
   :header-rows: 1
   :widths: 12 30 28 30

   * - Method
     - Path
     - Purpose
     - Success status
   * - ``GET``
     - ``/health``
     - Reports that the API process is running.
     - ``200 OK``
   * - ``POST``
     - ``/api/v1/questions``
     - Answers a question using the indexed documents.
     - ``200 OK``

The API has no authentication. Anyone who can reach the port can call it, so
expose it only on networks you trust.

Interactive documentation
-------------------------

FastAPI generates the documentation from the same route and schema definitions
that the server uses, so it is always current. While the server is running:

.. list-table::
   :header-rows: 1
   :widths: 25 75

   * - URL
     - Description
   * - ``http://127.0.0.1:8000/docs``
     - Swagger UI. Lets you send requests from the browser.
   * - ``http://127.0.0.1:8000/redoc``
     - ReDoc. A read-only view of the same endpoints and schemas.
   * - ``http://127.0.0.1:8000/openapi.json``
     - The raw OpenAPI 3.1 document. The reference on this page is generated
       from a copy of this document at build time.

Health check
------------

``GET /health`` returns a fixed payload. It does not contact the language model
or the embedding provider, so a healthy response does not prove that questions
can be answered. Use it to check that the process is up.

.. code-block:: console

   $ curl http://127.0.0.1:8000/health
   {"status":"ok"}

Question answering
------------------

``POST /api/v1/questions`` accepts a JSON body, runs the RAG workflow, and
returns the answer together with the retrieved documents that supported it.

.. code-block:: console

   $ curl -X POST http://127.0.0.1:8000/api/v1/questions \
       -H "Content-Type: application/json" \
       -d '{"question": "Which web framework does RAGdoll use?"}'

Request body
~~~~~~~~~~~~

The body is a :class:`~app.api.schemas.QuestionRequest` object.

.. list-table::
   :header-rows: 1
   :widths: 20 15 65

   * - Field
     - Type
     - Rules
   * - ``question``
     - string
     - Required. Leading and trailing whitespace is removed first. The result
       must contain between 1 and 2000 characters. A whitespace-only value is
       rejected.

Unknown fields are ignored; they do not cause a validation error.

Response body
~~~~~~~~~~~~~

The response is a :class:`~app.api.schemas.QuestionResponse` object.

.. list-table::
   :header-rows: 1
   :widths: 20 25 55

   * - Field
     - Type
     - Meaning
   * - ``answer``
     - string
     - The generated answer.
   * - ``sources``
     - list of objects
     - The retrieved chunks used to produce the answer. Empty when no relevant
       chunk was found.

Source documents
~~~~~~~~~~~~~~~~

Each entry in ``sources`` is a :class:`~app.api.schemas.SourceDocument`.

.. list-table::
   :header-rows: 1
   :widths: 20 20 60

   * - Field
     - Type
     - Meaning
   * - ``document_name``
     - string or ``null``
     - The file name of the Markdown document (the ``source`` metadata). For
       example ``overview.md``.
   * - ``section``
     - string or ``null``
     - The section within the document. The indexing pipeline does not record
       sections, so this is currently always ``null``.
   * - ``content``
     - string
     - The text of the retrieved chunk. This is the passage the answer is based
       on.
   * - ``metadata``
     - object
     - All metadata stored with the chunk. It contains ``source`` (the file
       name) and ``relative_path`` (the path below the documents directory,
       with forward slashes, for example ``guides/install.md``).

Example response
~~~~~~~~~~~~~~~~

The following response is a real serialisation produced by the endpoint code.
The document was supplied by a stub workflow, so the answer text is
illustrative. With a configured model, ``answer`` is generated by the model.

.. code-block:: json

   {
     "answer": "RAGdoll uses FastAPI.",
     "sources": [
       {
         "document_name": "overview.md",
         "section": null,
         "content": "RAGdoll uses FastAPI for its HTTP API.",
         "metadata": {
           "source": "overview.md",
           "relative_path": "overview.md"
         }
       }
     ]
   }

When no chunk is retrieved, the chat model is not called. The response carries
a fixed answer and an empty ``sources`` list:

.. code-block:: json

   {
     "answer": "I could not find any relevant information in the knowledge base to answer this question.",
     "sources": []
   }

Status codes
~~~~~~~~~~~~

.. list-table::
   :header-rows: 1
   :widths: 12 35 53

   * - Status
     - Cause
     - ``detail`` in the body
   * - ``200 OK``
     - The question was answered.
     - Not applicable.
   * - ``422 Unprocessable Entity``
     - The body is missing ``question``, the value is not a string, it is empty
       after stripping whitespace, or it is longer than 2000 characters.
     - A list of validation errors from FastAPI. Each error includes the
       rejected ``input``, so a very long question is echoed back in full.
   * - ``500 Internal Server Error``
     - An unexpected error occurred while answering. The details are logged on
       the server.
     - ``An unexpected error occurred.``
   * - ``502 Bad Gateway``
     - The chat model failed to generate an answer, for example because the
       provider rejected the request.
     - ``The language model failed to generate an answer.``
   * - ``503 Service Unavailable``
     - Document retrieval failed, or the question service could not be built
       (for example, a missing API key or an unavailable embedding model).
     - ``Document retrieval is currently unavailable.`` for retrieval failures,
       or ``The question service is not available.`` if the service could not
       be initialised.

Validation examples
~~~~~~~~~~~~~~~~~~~

With a working question service, a question that is only whitespace is rejected
before the workflow runs:

.. code-block:: console

   $ curl -X POST http://127.0.0.1:8000/api/v1/questions \
       -H "Content-Type: application/json" -d '{"question": "   "}'
   {"detail":[{"type":"string_too_short","loc":["body","question"],"msg":"String should have at least 1 character","input":"   ","ctx":{"min_length":1}}]}

Missing fields and wrong types produce a similar ``422`` error with
``"type": "missing"`` or ``"type": "string_type"``.

.. note::

   The question service is built on the first request that reaches it, not at
   start-up. FastAPI runs that dependency before it checks the body. So if the
   service cannot be built (for example, a missing API key), a request with an
   invalid body also returns ``503`` rather than ``422``. Send a valid request
   to confirm that the service is working.
